# 每次25个文件，合计500 MB

前后端统一按 `1024 * 1024` 字节计算页面标注的 MB。每次最多25个 JPG、PNG、MP4 文件，文件字节合计不超过500 MB；每条记录累计最多25个文件。图片单张8 MB、视频单个100 MB、家庭总空间5 GB限制继续生效。500 MB 是每次新选文件合计，不是整条记录累计大小。

前端在选择文件和保存前校验，追加文件时提示当前已有数量。后端在文件处理前检查数量，在持有家庭行锁的事务内再次核对累计数，防止并发追加突破25个。上传校验失败不删除已有文件。

Spring 和 Nginx 总请求上限设为501 MiB，给 multipart 边界和表单头预留1 MiB，业务层仍严格限制文件合计500 MiB。Tomcat `max-part-count` 显式设置50，容纳25个文件分段；该配置含义见 [Tomcat HTTP Connector 文档](https://tomcat.apache.org/tomcat-11.0-doc/config/http.html)。`file-size-threshold: 0B` 保持文件落盘，Kubernetes 的 `app-temp` 从1 GiB调整为2 GiB，为请求原文件与校验／重编码副本留空间。并发大上传或高膨胀比图片仍受实际临时磁盘容量限制。

## 本地使用

手动编译、重启并刷新页面，加载新的 `application.yml` 及前端脚本即可。无需数据库迁移。

## 线上部署时同步

此项目通过 `SPRING_CONFIG_LOCATION` 使用外部配置；已有 Nacos、ConfigMap 不会读取新 JAR 的默认值。先备份现有 Nacos 配置、`shiguang-bootstrap` ConfigMap 和 Deployment，再执行以下增量更新。

1. 将 `deploy/k8s/upload-nacos-snippet.yaml` 合并到 Nacos 的 `public / SHIGUANG / springai-demo.yaml`。保留其他 spring 配置及 server.tomcat 线程配置，避免创建重复的顶层节点。
2. 把新版 `deploy/k8s/nginx.conf` 上传到服务器的 `/opt/apps/shiguang-media/deploy/nginx.conf`。在服务器执行以下命令，只修改 ConfigMap 中的 nginx 文件，保留 `fetch_nacos.py` 等其他键：

```bash
cd /opt/apps/shiguang-media
python3 - <<'PY'
import json, pathlib, subprocess
patch = {'data': {'nginx.conf': pathlib.Path('deploy/nginx.conf').read_text()}}
subprocess.run(['kubectl', '-n', 'shiguang', 'patch', 'configmap', 'shiguang-bootstrap',
                '--type=merge', '--patch-file=/dev/stdin'],
               input=json.dumps(patch), text=True, check=True)
PY
```

3. 同步上传服务器上的新版 `resources.yaml`，保留这次实际新镜像标签。现有 Deployment 的卷可以按名称增量调整，以下操作会触发 Pod 重建并读取新的 Nacos 配置和 Nginx 文件：

```bash
kubectl -n shiguang patch deployment shiguang --type=strategic \
  -p '{"spec":{"template":{"spec":{"volumes":[{"name":"app-temp","emptyDir":{"sizeLimit":"2Gi"}}]}}}}'
```

4. 按常规步骤打包、导入新应用镜像并执行 `kubectl set image`，等待 rollout 成功。如果卷已经是2 GiB且镜像标签也没变化，需显式 `kubectl -n shiguang rollout restart deployment/shiguang` 才会重新加载配置。Nginx 使用 subPath 挂载，不依赖 ConfigMap 更新自动热加载。

- 5个各100 MiB的合法 MP4 合计500 MiB允许提交，合计超过500 MiB拒绝；单个文件和家庭容量上限仍正常执行。
